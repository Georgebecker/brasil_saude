# Migração para PostgreSQL/Oracle e para a nuvem

> Este documento é um **roadmap honesto**, não um anúncio. O projeto atual é
> local, didático e roda em SQLite. Nada aqui foi executado em produção.

## 1. Ponto de partida

| Dimensão | Hoje |
|---|---|
| Banco | SQLite (arquivo único, WAL) |
| Volume | ~2,3 MB; 5 tabelas de fato |
| Concorrência | 1 processo de coleta + leituras da API |
| Deploy | máquina local, `uvicorn` |
| Backup | cópia verificada + retenção de 7 |
| Autenticação | protótipo RBAC local |

O que **não** é problema hoje: volume, concorrência e disponibilidade. A
migração só se justifica quando um desses três mudar (ou quando o órgão exigir
SGBD homologado).

## 2. Para PostgreSQL (recomendado como primeiro passo)

### 2.1 Passos

1. Subir PostgreSQL 16 (container) e criar base + usuário de aplicação.
2. Traduzir o DDL:
   - `INTEGER PRIMARY KEY AUTOINCREMENT` → `GENERATED ALWAYS AS IDENTITY`;
   - `TEXT` → `text` (ou `varchar(n)` com limite explícito);
   - `ON CONFLICT ... DO UPDATE` → `INSERT ... ON CONFLICT ... DO UPDATE` (igual);
   - `PRAGMA` sai; criar `CHECK` e `FOREIGN KEY` normalmente;
   - datas ISO continuam `text` (ou migrar para `date`).
3. Criar migrações versionadas (Alembic) — o SQLite de hoje usa
   `_garantir_colunas`, que não escala.
4. Trocar o driver: `sqlite3` → `psycopg` (com *connection pool*).
5. Reescrever as consultas que usam `date(u.data_max, '-7 days')` para
   `u.data_max - interval '7 days'`.
6. Rodar a suíte contra PostgreSQL (fixture parametrizada).
7. Exportar/importar dados com `COPY` (não `INSERT` linha a linha).

### 2.2 O que é reaproveitado

- modelagem e chaves;
- serviços (`src/servicos/`) e regras (EARS);
- rotas e modelos Pydantic;
- frontend inteiro;
- testes de regra (só muda a fixture de conexão).

### 2.3 Riscos

| Risco | Mitigação |
|---|---|
| Dialeto SQL diferente | teste de integração com o banco real |
| Transações e concorrência | `SERIALIZABLE`/`READ COMMITTED` explícito |
| Datas como texto | migrar para `date`/`timestamptz` com validação |
| Perda de simplicidade local | manter `docker compose` de um comando |

## 3. Para Oracle

### 3.1 O que muda de verdade

| SQLite | Oracle |
|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `NUMBER GENERATED BY DEFAULT AS IDENTITY` |
| `TEXT` | `VARCHAR2(n)` / `CLOB` |
| `ON CONFLICT` | `MERGE` |
| `LIMIT/OFFSET` | `FETCH FIRST n ROWS ONLY` / `OFFSET` |
| `PRAGMA foreign_keys` | sempre ligado por definição |
| `date(x, '-7 days')` | `x - INTERVAL '7' DAY` |
| `sqlite3` Python | `python-oracledb` |

### 3.2 O que seria necessário

- tablespaces separadas para dados e índices;
- usuário de aplicação com privilégios mínimos;
- RMAN + archivelog;
- se alta disponibilidade: RAC (2 nós + ASM) e Data Guard;
- monitoramento (AWR/ASH) e plano de capacidade.

### 3.3 Exadata

Só faz sentido com volume e carga analítica que justifiquem *Smart Scan* e
*storage cells*. Para o volume atual (< 10 MB), é overkill — e o documento diz
isso em vez de vender complexidade.

## 4. Para AWS

```
Route 53 → ALB → ECS/Fargate (API)  → RDS PostgreSQL (Multi-AZ)
                                   → S3 (backup + artefatos)
                                   → Secrets Manager (credenciais)
                                   → CloudWatch (logs/métricas)
```

| Etapa | Serviço | Observação |
|---|---|---|
| API | ECS Fargate ou EC2 | imagem Docker da aplicação |
| Banco | RDS PostgreSQL Multi-AZ | backup automático + PITR |
| Backup extra | S3 com versionamento e lifecycle | cópia fora da conta de produção |
| Segredos | Secrets Manager | nada em `.env` no container |
| CI/CD | GitHub Actions + OIDC | sem chave estática |
| Observabilidade | CloudWatch + alarms | SLO de disponibilidade |

## 5. Kubernetes (fase posterior)

- Deployment da API + HPA;
- StatefulSet ou operador (CloudNativePG) para o banco;
- CronJob para a coleta (substitui o timer);
- ConfigMap/Secret para configuração;
- NetworkPolicy restringindo o banco.

Não é prioridade: o ganho aparece com múltiplos serviços e times, não com um
painel de leitura.

## 6. Plano de migração em fases

| Fase | Entrega | Critério de saída |
|---|---|---|
| 0 (hoje) | SQLite + backup verificado | 63 testes verdes |
| 1 | PostgreSQL local via Docker | suíte verde contra Postgres |
| 2 | Migrações versionadas | `alembic upgrade head` do zero funciona |
| 3 | Deploy em nuvem | API responde com TLS; backup no S3 |
| 4 | Réplica + failover | ensaio documentado com RTO medido |
| 5 | Oracle (se exigido) | RMAN + restore validado em ambiente separado |

## 7. Rollback

Em qualquer fase: manter o SQLite como *fallback* de leitura e o backup
verificado. A migração é sempre **cópia**, nunca *move* — o banco antigo fica
intacto até a nova fase provar que funciona.
